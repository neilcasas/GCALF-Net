## Stage 1 — Throughput measurement and M5 budget record

### The fork/CUDA hang (found and fixed)

Reproduced the exact risk the plan flagged: with `augment_cfg.multiprocessing=true`, all 15
`MultiThreadedAugmenter` worker processes deadlocked permanently at 0% CPU, forked *after* Lightning
had already initialized a CUDA context on the main process. Confirmed via process state (workers
sleeping indefinitely, GPU at 0% util) — not a slow first batch.

**Fix**: `scripts/train.py`, `if __name__ == "__main__":` block now calls
`multiprocessing.set_start_method("spawn", force=True)` before `train()`. Verified live: training
proceeded normally past the point that previously hung, both epochs of a 2-epoch test completed with
real checkpoints written. One cosmetic side effect: a harmless teardown-time exception from
`batchgenerators`' worker-cleanup threads racing process exit, occurring only after all real work
(checkpoints, metrics) is already saved.

Evidence: `evidence/stage1-mp16-hang-20260915/` (the hang), `evidence/stage1-mp16-spawn-20260915/`
(the fix, verified).

## Stage 2 — Anchor-class diagnostic

Root cause note: the anchor-counting instrumentation existed in the local repo's uncommitted working
tree but had never been synced to the instance checkout, so the first attempt
(`evidence/stage2-anchor-20260916/`, no data) silently produced nothing. Fixed by syncing all 24
modified/untracked files from local to `/workspace/GCALF-Net-corrected` (tarball transfer), which also
surfaced and fixed one real bug: `tests/gcalf/test_grade_sampling.py` used `str.removeprefix`
(Python 3.9+ only) against the pinned Python 3.8 environment — corrected to `str[len(prefix):]`.

Re-run (`evidence/stage2-anchor-20260916-v2.log`) measured the real sampled-anchor distribution after
positive-anchor subsampling — the actual class prior the grade CE sees, as opposed to lesion-count
metadata:

| | Sampled anchors | Share | Lesion-count share (current weighting basis) |
|---|---|---|---|
| GGG2 | 58,156 | 57.5% | 57.4% |
| GGG3 | 23,248 | 23.0% | 23.6% |
| GGG4 | 8,991 | 8.9% | 8.4% |
| GGG5 | 10,725 | 10.6% | 10.7% |

**Key finding**: the anchor-level and lesion-level priors are nearly identical. Anchor-based
class weights (`[0.260, 0.650, 1.681, 1.409]`) differ from the current lesion-based weights
(`[0.256, 0.622, 1.747, 1.376]`) by only 2–5% per class. Fix A's premise — that the CE sees a
materially different, more extreme imbalance than lesion counts imply — does not hold under
measurement. This predicts Fix A would not meaningfully change training dynamics.

## Stage 3 — The fix attempt

### Decision: Fix A skipped, Fix B run directly

Documented as an explicit, disclosed protocol deviation in `docs/adr/0003-endpoints-grade-monitor-and-patience.md`
(2026-09-16 entry): given Stage 2's evidence that anchor-based reweighting would reproduce the
existing lesion-based weights within 2-5%, Fix A's 13-epoch pilot (predicted to fail) was not run.
Fix B (`gcalf_grade_remediation`, uniform GGG2–5 sampling among supervised foreground lesions) was
run directly instead.

### Fix B pilot result: fails the gate

13-epoch, fold-0-only pilot (`train=gcalf_grade_remediation`, `augment_cfg.multiprocessing=true`,
spawn-fixed). Training completed cleanly (all 13 epochs, real checkpoints:
`model_best.ckpt`/`model_last.ckpt`/`model_best_grade.ckpt`). Grade-balanced sampling confirmed active
in the logs (e.g. training cache `GGG2=204, GGG3=82, GGG4=30, GGG5=38`, vs. the old regime's roughly
4% GGG4 patch exposure).

**Official evaluation** (`python -m gcalf_eval.run_eval`, case-level, TTA, `--grade-score-threshold
0.05` per the declared operating point), saved at `evidence/stage3-fixb-20260916/run_eval.log`:

```
grade_confusion_matrix: [[0,22,7,12],[0,4,4,10],[0,0,2,3],[0,4,3,2]]
grade_balanced_accuracy: 0.2111
grade_per_class_sensitivity: {GGG2: 0.0, GGG3: 0.222, GGG4: 0.400, GGG5: 0.222}
```

Column sums (predicted): GGG2 = **0**, GGG3 = 30, GGG4 = 16, GGG5 = 27.

**Fix B overcorrected.** GGG4 is now genuinely predicted (16 times, sensitivity 0.40 — a real fix for
the original problem), but GGG2 — the majority class — is now *never* predicted at all. The
non-emission failure mode persists, just relocated to a different class. `grade_balanced_accuracy`
(0.211) is well below the pre-declared >0.33 threshold. **Primary and secondary gate criteria both
fail.**

Full training log: `evidence/stage3-fixb-20260916/train.log` (13 epochs' worth of confusion matrices,
showing the progressive swing from GGG2-collapse toward GGG2-elimination as balanced sampling took
effect). Real anchor counts for this specific run: `evidence/stage3-fixb-20260916/grade_anchor_counts.json`.

## Where this leaves the matrix launch

- **M5/budget: unblocked.** Folds 1–4 and the 20-run matrix are clear on the compute-budget side.
- **Grade-remediation gate (ADR 0003): still blocking.** Fix A skipped on strong Stage 2 evidence
  (not empirically tested); Fix B empirically tested and failed. Per the plan's own fallback: the
  next authorized step is Fix C (ordinal loss — not implemented, would need new code and a fresh
  validation cycle), or reverting to the locked configuration and reporting the grade result as a
  documented null. **No fix currently passes the gate; the matrix should not launch on the grade
  question as it stands.**
- Both fixes point at the same underlying issue rather than a sampling/reweighting bug: GGG4 has
  only 37 total supervised lesions (~30 per training fold) — a genuine small-n limit neither
  reweighting (Fix A) nor resampling (Fix B) can manufacture past, because both only redistribute
  exposure to the same fixed set of examples rather than adding new information. This matches the
  plan's own pre-registered acknowledgment that GGG4 performance may hit a real information ceiling.
