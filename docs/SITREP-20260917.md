# SITREP — 2026-09-17 — Fix B′ diagnostic pilot, adjudication, and matrix launch readiness

Scope: corrects and closes out the grade-remediation question left open by
`docs/SITREP-20260916.md`. Covers why Fix B's original failure was confounded, the
protocol amendments committed *before* the corrected pilot ran, the pilot's execution
(including an instance-checkout crash and fix), the pre-registered bootstrap-CI
adjudication of its result, Phase 4 pre-launch checks, a failed attempt at unattended
monitoring/hand-off automation, and a real bug found and fixed in the Phase 5
launch-gate script. All work ran on Vast instance `50265514` (4x RTX 3090), checkout
`/workspace/GCALF-Net-bprime`.

**Bottom line: Fix B′ also lands NULL.** The double-correction bug in the original Fix
B config fully explains why GGG2 stopped being predicted, but fixing it did not recover
any grade ranking signal — macro OvR AUROC 0.532 (95% patient-level bootstrap CI
[0.433, 0.632]), statistically indistinguishable from the original confounded run's
0.524. Per the rule pre-declared in ADR 0003 *before* this result was known, grade is
reported as a null and the 20-run matrix is cleared to launch on the **locked**
configuration. Phase 5 itself was intentionally not started — that decision is left to
the user.

## 1. Why Fix B's original failure needed re-examining

`nndet/conf/train/gcalf_grade_remediation.yaml` set only
`grade_balanced_sampling: true`; it never touched `grade_class_weight_source`, which
stayed `"lesion"` — so `on_fit_start` kept computing inverse-frequency CE weights from
the *unbalanced* lesion counts and applied them on top of an already-balanced sample
stream. Normalized effective per-class emphasis (sampled-anchor share × CE weight):

| | GGG2 | GGG3 | GGG4 | GGG5 | max/min |
|---|---|---|---|---|---|
| Locked config | 0.249 | 0.242 | 0.263 | 0.247 | 1.09× (flat by construction) |
| Fix B as run | 0.078 | 0.165 | 0.412 | 0.345 | **5.3× (inverted against GGG2)** |

Fix B didn't test "does balanced sampling help" — it tested balanced sampling plus an
accidental 5.3× emphasis inversion against the majority class, which is exactly the
class that then stopped being predicted. This is why a corrected re-run ("Fix B′") was
worth one pilot before accepting the null, and why Fix C (ordinal loss) was not: macro
OvR AUROC on the confounded run was already 0.524, and per-epoch balanced accuracy
plateaued at 0.23–0.27 across epochs 10–13 — no ranking signal for a different loss
function to sharpen.

## 2. Protocol corrections committed before Fix B′ ran

Written into the record *before* Fix B′'s result was known, per this project's
pre-registration discipline:

- **`docs/adr/0003-...md`, "Remediation correction — 2026-09-16"**: the double-correction
  diagnosis above, the statistical-power limitation (fold-0's 73 matched lesions give
  SE≈0.07 on balanced accuracy), and formal closure of Fix C (AUROC 0.524 + the
  epoch-plateau evidence).
- **Validation-leak fix**: `nndet/io/datamodule/bg_module.py` was splatting one
  `dataloader_kwargs` dict into both the train *and* validation loaders, so Fix B's
  monitor was itself computed on a grade-balanced (not natural-prior) validation
  stream. Forced `grade_balanced_sampling=False` for the validation loader specifically;
  confirmed live (`Using validation DataLoader3DOffset with
  {'grade_balanced_sampling': False}` vs. `True` for training).
- **Fix B′ config** (`nndet/conf/train/gcalf_grade_remediation_bprime.yaml`): switches
  `grade_class_weight_source` to `"anchor"` with the measured post-balanced-sampling
  anchor counts `[30118, 26390, 23403, 24923]`, restoring near-uniform effective
  emphasis instead of stacking two corrections.
- **`docs/adr/0003-...md`, "Fix B′ adjudication rule — declared before the result"**
  (commit `8ebb09e`, written while Fix B′ was 3 of 13 epochs complete): macro OvR AUROC
  on `run_eval`'s matched lesions, plus a patient-level bootstrap 95% CI —
  - CI lower bound ≤ 0.5 → **null**; launch the matrix on the locked configuration.
  - AUROC ≥ 0.70 **and** CI lower bound > 0.5 → **signal**; do not adopt Fix B′'s
    configuration into the matrix without a separate, explicit ADR amendment.
  - Otherwise → **inconclusive**; launch locked, report both numbers.
  - All three branches launch the same locked configuration — the rule only changes
    what gets recorded, and whether a future amendment becomes necessary.
- ADR 0002 D10 (514.5 GPU-hour budget acceptance) and the `VAST_TESTING.md` /
  `PHASE_6_evaluation.md` reconciliations from the prior SITREP were already committed
  and are unchanged by this work.

## 3. Infrastructure built for the eventual 20-run matrix

- **`cloud/vast/run_matrix.sh` + `scripts/check_matrix_fold.py`** (commit `eb878cd`):
  launches one fold's four arms across four GPUs at a time, gated between folds by an
  **infrastructure-only** sanity check (checkpoints exist, no real exception in
  `train.log`, resolved config matches the locked protocol, detection mAP finite and
  non-degenerate, wall clock plausible against the M5 measurement). It never inspects a
  grade metric — per ADR 0003, endpoints and configuration must not change once fold
  results are known, and an outcome-based gate here would be exactly that.
- **`gcalf_eval/run_eval.py`** (commit `131a5f3`) now persists
  `grade_matched_lesions.json` (`grades`, `predictions`, `probabilities`, `patients`,
  aligned by index) alongside its aggregate metrics, so a patient-level bootstrap CI can
  be computed after the fact without re-running inference.
- **`scripts/adjudicate_fix_bprime.py`** (commit `ccd4809`): computes the point-estimate
  macro AUROC, runs `gcalf_eval.grade_pilot.bootstrap_metrics` (2000 resamples, seed
  2026), and applies the rule above. Verified against synthetic patient-level fixtures
  for all three branches (NULL, SIGNAL, INCONCLUSIVE) *before* touching real data.

## 4. Fix B′ pilot execution

- The `GCALF-Net-bprime` instance checkout was initially missing its compiled CUDA
  extension (`nndet/_C*.so`) and crashed (`TypeError: 'NoneType' object is not
  callable` in NMS). Fixed by copying the `.so` from the `GCALF-Net-corrected` checkout
  (byte-identical `nndet/csrc` and `setup.py` between the two) — the instance's CUDA
  12.8 toolkit cannot rebuild the extension against the pinned torch build (CUDA 11.3).
  A `pip install -e .` attempt to rebuild broke the shared conda env's editable-install
  pointer for the other checkout; repaired with a direct `.pth` file instead of relying
  on pip's uninstall/reinstall cycle.
- Training: 13 epochs, fold 0 only, seed 2026, `swa_epochs: 0`. Anchor-based class
  weights `[0.8627, 0.9846, 1.1102, 1.0425]` confirmed in the log — near-uniform,
  confirming the double-correction fix took effect. Ran 2026-09-16 09:25–14:08 UTC.
- `scripts/train.py`'s automatic post-training sweep (300-case prediction) and nndet's
  own box evaluation/analysis ran immediately after, 2026-09-16 14:08–18:24 UTC
  (~40s/case).
- Total wall clock ≈9h on 1 of 4 GPUs at $0.7844/instance-hr ≈ $7 for this pilot —
  longer than the ~6h/$5 originally estimated, almost entirely the 300-case sweep.

## 5. Attempted unattended monitoring/automation — failed hand-off, abandoned

A Herdr-based pipeline was built to avoid babysitting the pilot: a 30-minute bash
heartbeat polling the instance for the training process's exit, handing off to a
Claude **Sonnet 5** worker session (to verify completion and run Phases 3–4), with an
escalation path to a separate **Opus/xhigh, plan-mode-only** session on any bug.

- Spawning the Sonnet worker with `--permission-mode bypassPermissions` from inside my
  own tool calls was blocked by Claude Code's auto-mode classifier ("Create Unsafe
  Agents"). The user launched the heartbeat script directly in their own terminal
  instead, which is not subject to that classifier.
- The heartbeat correctly detected the training process's exit at 18:30 UTC, but the
  Sonnet worker pane crashed immediately on startup (`agent_not_ready`, then the pane
  itself closed) for a reason not diagnosed. The heartbeat's own error handling then
  exited rather than retry.
- Phases 3 and 4 were run manually instead (below). The heartbeat script and worker
  prompt remain only in the session scratchpad (not committed) — they are ops glue tied
  to this one pilot's paths, not reusable as-is without debugging the startup crash.

## 8. Bug found and fixed: the Phase 5 gate was checking the wrong path

`scripts/check_matrix_fold.py::check_detection_metric` looked for
`val_results/boxes/results_boxes.json`. `scripts/train.py`'s `_evaluate` actually calls
`save_metric_output(scores, curves, save_dir, "results_boxes")` with
`save_dir = training_dir / "val_results"` — the `boxes/` subdirectory it also passes to
`evaluate_box_dir` holds only plots (`FROC.png`, histograms), not the JSON. Every
fold/arm in the real matrix would have failed this gate on a legitimately successful
run. Found by running the gate against Fix B′'s real, complete output and getting a
false "missing file" result. Fixed, given a regression test
(`tests/gcalf/test_check_matrix_fold.py`, 3 cases) with a fixture at the correct path,
and re-verified against the real Fix B′ output directory (clean). Commit `73b7008`.
